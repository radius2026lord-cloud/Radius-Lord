# Backup filenames and batch ZIP downloads

Backup artifacts retain their internal server path. User-facing downloads and new cloud uploads are named database_YYYY-MM-DD_HH-mm-ss.sql.gz. New backup requests record the backup policy timezone in job metadata; phase and verification updates merge metadata rather than replacing it. The timestamp uses the remote backup start time when present, otherwise request creation. Legacy jobs without a timezone use the current backup policy timezone as fallback. This does not rename the MySQL database or old files already uploaded to a cloud provider.

The batch download button first shows available/total counts. Preparation captures the latest attempt for each target and includes only verified successful files whose server artifact is not marked removed. If a source disappears or its bytes/SHA-256 fail verification while preparing, preparation fails without publishing a partial ZIP.

Only one archive is prepared at a time per backend process. SSH reads and local disk writes run sequentially with bounded stream buffering. Already compressed .sql.gz files are stored without additional ZIP compression. ZIP64 records permit large archives, and CRC32 is written for each entry. SHA-256 is checked against the verified job record before the archive is published. The archive includes manifest.json with included and unavailable targets, filenames, backup timestamps, timezone and hashes; no credentials or cloud tokens are included.

Preparation state and download authorization are scoped to the requesting central admin. The UI polls an in-memory status endpoint and retains its task ID in sessionStorage for reopening the tab. Download uses the browser's native file transfer rather than buffering a ZIP in browser memory. A ready archive expires after 30 minutes; failed-task state expires after 10 minutes. A backend restart loses in-memory task handles, requiring preparation again; stale on-disk folders older than a day are cleaned when preparation next runs. Temporary files live under the backend OS temporary directory, separate from server backup retention. Available disk space is checked before writing. Actual server/cloud access and archive extraction still require live verification after deployment.
