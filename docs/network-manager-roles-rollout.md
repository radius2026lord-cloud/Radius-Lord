# أدوار مستخدمي الشبكة — القاعدة الحالية

هذه المرحلة تخص قاعدة الزبون `rl_tenant_zone_000003` فقط. لا تغيّر قوالب تجهيز البيئات الجديدة أو بيانات المنصة المركزية.

## التطبيق

1. التوسعة الأولى التي سبق تطبيقها مطلوبة: حقول الأدوار والنطاقات وجداول النطاقات وأرقام التواصل.
2. أخذ نسخة احتياطية من قاعدة الزبون وإيقاف كتابات الباك إند مؤقتًا.
3. تنفيذ الملف الكامل `src/app/backend/tenant-upgrades/customer_000003_manager_roles.sql` في قاعدة الزبون. في phpMyAdmin استخدم الاستيراد أو الصق الملف كاملًا؛ لا تنفذ أجزاء من الإجراء منفردة. لا تضف علامات سياج Markdown.
4. تحديث المشروع وتشغيل الباك إند والواجهة مجددًا.

الترقية تصنف المدير الرئيسي، وتحفظ لكل موظف قديم نطاقًا خاصًا سابقًا مع نسخة من مجموعته الحالية، وتملأ نطاقات سجلاته دون تغيير حقول الملكية القديمة. المجموعات الأصلية تصبح ضمن المركز. لا تمنح صلاحيات الوكلاء تلقائيًا. أسماء المجموعات فريدة ضمن نطاقها بدل أن تكون فريدة على مستوى الشبكة كلها. الترقية قابلة لإعادة التنفيذ؛ البيانات المصنفة لا يعاد تصنيفها. DDL يثبت تلقائيًا؛ عند فشل خطوة بنيوية افحص السبب ثم أعد تنفيذ الملف، ولا تفترض أن ROLLBACK يعكس DDL.

## الاستخدام

- موظف المركز الجديد: اختر مجموعة ضمن المركز.
- وكيل جديد: أنشئ مجموعة بنطاق «مجموعة مستقلة لوكيل جديد»، ثم اخترها عند إنشاء الوكيل. تُربط المجموعة والنطاق بالوكيل في معاملة واحدة، ولا يجوز أن تكون المجموعة مستخدمة من حساب آخر.
- موظف الوكيل: اختر الوكيل ثم مجموعة ضمن نطاقه لا تتجاوز صلاحياته.
- الوكيل المخوّل بـ `agents.staff.manage` يدير موظفيه فقط. `agents.staff_groups.manage` يتيح إدارة مجموعات موظفيه ضمن نطاقه دون تعديل مجموعته الشخصية.
- نسخ المجموعة يحتفظ بنطاقها وصلاحياتها دون نقل مستخدميها. لتغيير نسخة مستقلة عدّلها بعد إنشائها ثم أسندها للحسابات المطلوبة.
- تغيير الدور أو الوكيل المسؤول لحساب قائم ممنوع ضمن التعديل العادي، لتجنب نقل ملكية السجلات عرضًا.
- تعطيل الوكيل يمنع دخول موظفيه ويبطل جلساتهم. تغيير مجموعة الوكيل يبطل جلسات موظفيه ويحد صلاحياتهم بتقاطع المجموعتين. لا تُعدّل حسابات RADIUS أو المشتركين عند التعطيل.
- كلمات المرور مخزنة بتجزئة bcrypt؛ لا تدخل في سجل النشاط. لا تنفذ هذه المرحلة MFA أو إعداد شهادة HTTPS المؤجلين.

## حدود هذه المرحلة

تنفذ إدارة المستخدمين ومجموعات الصلاحيات والتحقق من الدخول والجلسات. إدارة التصنيفات والمشتركين وفق النطاقات ستُبنى في مرحلتها؛ صفحات بيانات المشتركين والبروفايلات والهوتسبوت الحالية تبقى محمية للمدير الرئيسي. صلاحية `customers.view_center_scope` مسجلة للاستعمال في تلك المرحلة، ولا تمنح وصولًا لصفحات غير مكتملة الآن. مفاتيح علاقات التصنيف القديمة تبقى محفوظة حتى الترقية المنسقة لتلك الصفحات.

## تحقق بعد التطبيق

```sql
SELECT account_role, COUNT(*) AS accounts
FROM rl_tenant_zone_000003.managers GROUP BY account_role;
SELECT id, name, scope_kind, owner_manager_id
FROM rl_tenant_zone_000003.network_scopes;
SELECT COUNT(*) AS missing_roles
FROM rl_tenant_zone_000003.managers WHERE account_role IS NULL;
SELECT code FROM rl_tenant_zone_000003.permissions
WHERE code IN ('agents.staff.manage','agents.staff_groups.manage','customers.view_center_scope');
```

ينبغي أن يكون `missing_roles` صفرًا. جرّب إنشاء وكيل وموظف تابع له، منع منحه صلاحية خارج مجموعة الوكيل، تعطيل الوكيل والتحقق من منع دخول موظفه، تعديل مجموعة مشتركة مع عرض العدد، ثم نسخها والتأكد أن الحسابات لم تنتقل تلقائيًا. لا توجد اختبارات متصفح مشغلة ضمن هذه المرحلة؛ يجرب المستخدم الواجهة وفق قواعد المشروع.
