# تحديثات Radius Lord

## مرجع قاعدة الشبكة

قالب `src/app/backend/tenant-schema/create_tenant_database.sql` هو مرجع توليد قواعد العملاء. بُني من آخر تصدير معتمد، وتُضاف إليه تعديلات البنية عند اعتمادها. قاعدة `rl_tenant_zone_000003` للتطوير.
القيم المزروعة محصورة في قواميس التطبيق المرجعية، ثم تضيف مرحلة تجهيز البيئة
حساب المدير الجديد وبيانات الخطة والرخصة وتتحقق من اتصالات التشغيل.

عند اعتماد طلب تجهيز البيئة، يستورد العامل القالب مباشرة عبر MySQL، ثم
يسجل بصمة الملف وبصمة بنية القاعدة المستوردة ضمن سجل التجهيز. يعيد قراءة
بنية القاعدة قبل مواصلة التجهيز، ويقارنها بالبصمة المسجلة عند استئناف الطلب.
تُنفّذ إعدادات FreeRADIUS على الخادم عبر اتصال SSH المحفوظ في الباك إند.

الأمر التالي اختياري لفحص قالب إصدار من الطرفية، ويستخدم حساب MySQL
يمكنه إنشاء قاعدة اختبار مؤقتة وقراءة تعريفاتها وحذفها:

```bash
cd src/app/backend
npx ts-node scripts/verify-tenant-schema.ts --from-template
```

اضبط `SCHEMA_VERIFY_USER` في بيئة الطرفية مع متغيرات الاتصال اللازمة
`SCHEMA_VERIFY_HOST` و`SCHEMA_VERIFY_PORT` و`SCHEMA_VERIFY_PASSWORD` أو
`SCHEMA_VERIFY_SOCKET`. يطبع الأمر بصمة البنية لأغراض التحقق.

يطبّق الباك إند ترحيل القاعدة المركزية تلقائيًا عند اعتماد طلب تجهيز يدوي.
لتطبيقه مبكرًا عند تشغيل الإصدار، اضبط
`RADIUS_MIGRATE_MANUAL_ENVIRONMENT_ON_START=1` في عملية الباك إند التي تتصل
بالقاعدة المركزية. يلزم أن يملك حسابها صلاحيات الترحيل المحددة. الترحيل
محمي بقفل على المحرك ويتجاوز التنفيذ عندما تكون البنية المطلوبة موجودة.

## تجهيز حزمة للمراجعة

جهّز ملف ZIP محليًا من مخرجات البناء وملفات الترحيل المعتمدة. احتفظ بمفتاح
Ed25519 الخاص خارج المشروع وعلى جهاز الإصدار فقط. من مجلد الباك إند:

```bash
node scripts/sign-release.cjs v1.4.0 bundle.zip changes.txt private-key.pem
```

على الاستضافة، عيّن `RADIUS_RELEASE_STAGING_DIR` إلى مجلد دائم خارج جذر الويب
ويملك عامل الباك إند حق الكتابة فيه، واضبط `RADIUS_RELEASE_PUBLIC_KEY`
على المفتاح العام بصيغة PEM. اضبط `RADIUS_RELEASE_VERSION` على رقم الإصدار
المشغّل، و`RADIUS_RELEASE_TENANT_SCHEMA_VERSION` على إصدار بنية الشبكات
المعتمد للمقارنة مع النسخ المسجّلة. تأكد أن الوكيل الأمامي يسمح برفع الحزمة بالحجم المطلوب ضمن حد
التطبيق البالغ 100 MiB. ارفع الحزمة وملفي البيان والتوقيع من الإدارة المركزية
ضمن «النظام ← تحديثات النظام».

هذه المرحلة تحفظ الحزمة بعد فحص التوقيع والحجم والبصمة، وتعرض إصدارات قواعد
الشبكات المسجلة. نشر الحزمة وترحيلات قواعد الشبكات القائمة وسجل نتائج النشر
لكل شبكة تتطلب عامل النشر.

## النشر إلى Git على Ubuntu

يبقى التطوير في المستودع المعتمد وفرع `work/subscriptions-customer-details`. وجهة `hosting` في جهازك تستقبل وسم الإصدار المختار، ويطبق عامل مستقل على الخادم الإصدار بعد وصوله.

### تهيئة الخادم مرة واحدة

يلزم Ubuntu مع Node.js وnpm متوافقين مع ملفات قفل المشروع ومتاحين لحساب الخدمة على مستوى النظام. شغّل من نسخة موثوقة من المشروع.

```bash
sudo bash deployment/ubuntu/install-git-host.sh radiusdeploy /srv/radius-lord
```

ينشئ المثبّت مستودع `repository.git` وطابور نشر عبر systemd. جهّز مفتاح SSH لحساب `radiusdeploy` وتحقق من بصمة الخادم على جهاز الإصدار. يستخدم التطبيق `BatchMode` و`StrictHostKeyChecking` بالهوية المجهّزة.

أكمل الملفات التالية تحت `/srv/radius-lord/shared` بصلاحية قراءة لحساب الخدمة فقط.

- `root.env` لإعدادات واجهة الاستضافة.
- `backend.env` لإعدادات الباك إند والقاعدة والتشفير.
- `hooks/backup` عامل نسخ احتياطي قابل للتنفيذ.
- `hooks/migrate` عامل الترحيل المعتمد عندما يتغير SQL أو مجلد migrations.

يمكن نسخ `hooks/backup.example.sh` إلى `hooks/backup` بعد توفير mysqldump وضبط `shared/mysql-backup.cnf`. يحتاج الحساب صلاحيات قراءة القواعد والإجراءات والأحداث والمشغلات. المثال ينسخ قواعد المحرك ويتحقق من سلامة gzip ويحفظ SHA256. تجربة الاستعادة إلى محرك تجريبي جزء من اعتماد آلية النسخ.

اضبط عناوين الفحص في `host-config.json` إذا اختلفت المنافذ. يفحص العامل `/release-health` على الباك إند وصفحة تسجيل الدخول على الواجهة، ويطابق معرّف الإصدار المشغّل. المرفقات والشعارات في `shared/uploads`، والحالات في `status`، وسجلات التنفيذ في `logs`.

### تهيئة جهاز الإصدار

```bash
git remote add hosting radiusdeploy@HOST:/srv/radius-lord/repository.git
git config user.name "YOUR NAME"
git config user.email "YOUR EMAIL"
```

إذا كانت `hosting` موجودة فاستخدم `git remote set-url hosting ...`. اضبط الباك إند المحلي على مسارين مطلقين فعليين.

```dotenv
RADIUS_GIT_RELEASE_ENABLED=1
RADIUS_GIT_RELEASE_REPO=E:/LordRad/Project/lord-radius
RADIUS_GIT_RELEASE_STATE_DIR=E:/LordRad/release-state
```

مجلد الحالة خارج مستودع العمل. على Linux استخدم مسارك المطلق. اترك علامة التفعيل المحلية خارج إعدادات الاستضافة، وشغّل الباك إند بهوية المستخدم الذي جهّز Git وSSH.

بعد تنزيل التعديلات وتجربتها وحفظها على الفرع المعتمد، افتح تحديثات النظام. راجع معرّف المصدر ونظافة المجلد والوجهة، ثم افحص الجاهزية وأدخل رقم الإصدار والتغييرات وأكد تجربته محليًا. راجع الإصدار ثم أرسله. تستمر عملية الخادم بعد انقطاع جهازك.

نجاح Git يؤكد وصول الوسم. حالة `succeeded` تتطلب البناء والنسخ والترحيل المطلوب والتحقق من التشغيل. حالة `delivery_unknown` تتطلب تحديث السجل قبل إعادة الإرسال. يستعيد فحص الحالة إيصال الاستلام إذا وصل الوسم وتعطلت كتابة طابور post-receive. أرقام الإصدارات ثابتة، ويحتاج تصحيح إصدار فشل إلى رقم جديد.

### اتفاق النسخ والترحيل

العامل برنامج موثوق على الخادم خارج كود الإصدارات. يستقبل `RADIUS_RELEASE_MANIFEST` لمسار بيان الإصدار ومعرّف Git والملفات البنيوية المتغيرة، و`RADIUS_RELEASE_RESULT` لملف JSON يكتب فيه النتيجة.

يرجع النسخ `backupId` و`verified: true` بعد التحقق. قواعد الشبكات الحالية تُحدّث بترحيلات مرقّمة تحفظ نجاح كل خطوة وتدعم إعادة المحاولة بعد فشل جزئي. ملف توليد القاعدة الخام يستخدم للشبكات الجديدة.

مثال نتيجة الترحيل التالية يحتاج بصمة SHA256 فعلية من 64 محرفًا بعد مقارنة البنية بالقالب المعتمد.

```json
{
  "status": "succeeded",
  "central": {"status": "succeeded", "schemaVersion": "2026.11.1"},
  "expectedNetworkCount": 1,
  "networks": [
    {"tenantId": 3, "name": "Example", "status": "succeeded", "schemaVersion": "2026.11.1"}
  ],
  "tenantSchemaVersion": "2026.11.1",
  "tenantSchemaFingerprint": "REPLACE_WITH_VERIFIED_64_CHARACTER_SHA256",
  "backwardCompatible": true
}
```

`expectedNetworkCount` يحصي القواعد المستهدفة فعليًا. يجب أن تطابقه النتائج وتخلو من التكرار. عيّن `backwardCompatible` بعد التحقق من عمل الإصدار السابق على البنية الناتجة. عند الفشل يكتب العامل نتائج الشبكات ويعيد رمز خروج غير صفري.

يُوقف التطبيق أثناء الترحيل ثم يُفعّل الإصدار الجديد. إذا فشل التحقق، يُعاد التطبيق السابق ويُفحص عندما تكون البنية متوافقة معه. إذا بدأ ترحيل غير متوافق أو انقطع العامل، تظهر `recovery_required` ويتوقف الطابور حتى مراجعة النسخة الاحتياطية وحالة القواعد. بعد الاستعادة أو إتمام الترحيل والتحقق، يوثّق المسؤول الإجراء ويعيد اعتماد سجل الإصدار على الخادم قبل استكمال الطابور.
