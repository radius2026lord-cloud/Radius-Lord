# بيانات الشبكة ونطاقات الوكلاء — مخطط التعديل المعتمد

حالة هذا الملف: مواصفة تصميم قبل كتابة SQL الترقية. لا يغيّر مخطط قاعدة البيانات أو البيانات الحية. يخص قاعدة بيئة الزبون المعزولة، وليس lord_radius_core.

## بيانات الشبكة

يُمدد network_settings الموجود دون إنشاء بديل أو نقل بيانات الاشتراك إليه:

| الحقل | النوع المقترح | القاعدة |
|---|---|---|
| contact_email | VARCHAR(254) NULL | بريد التواصل الاختياري، يتحقق الخادم من صيغته |
| address | TEXT NULL | عنوان الشبكة |
| latitude | DECIMAL(10,7) NULL | من -90 إلى 90 |
| longitude | DECIMAL(10,7) NULL | من -180 إلى 180 |
| government_license_number | VARCHAR(100) NULL | ترخيص حكومي اختياري، نص للحفاظ على الأصفار والرموز |
| logo_reference | VARCHAR(500) NULL | مرجع ملف مُدار داخل بيئة الشبكة، لا مسار يختاره العميل |

يبقى network_name وdescription وtimezone وprimary_contact_phone كما هي. تستخدم الأرقام الإضافية network_contact_numbers مع phone وlabel وdisplay_order. يجب إدخال الإحداثيات معًا أو تركهما فارغتين. الترخيص الحكومي منفصل عن platform_subscription.license_number. إعدادات RADIUS وسياسة السماح لا تعرض ضمن نموذج البيانات العامة.

## الحسابات والنطاقات

يبقى manager_type بقيمتي principal/subordinate للحفاظ على قيد المدير الرئيسي الواحد. تضاف account_role بقيم principal/center_employee/agent/agent_employee. قيد CHECK يطابق principal مع manager_type=principal، وبقية الصفات مع subordinate. لا تُستنتج الصلاحيات من الصفة وحدها.

جدول network_scopes المقترح:

| الحقل | الغرض |
|---|---|
| id | مفتاح النطاق |
| scope_kind | center أو agent أو legacy_private |
| name | اسم النطاق |
| owner_manager_id | الوكيل المالك لنطاق الوكيل؛ وصاحب الملكية السابقة للنطاق الانتقالي |
| is_enabled | السماح باستخدام النطاق |
| created_by_manager_id | من أنشأ النطاق؛ اختياري فقط للإنشاء النظامي أثناء الترقية |
| archived_at / archived_by_manager_id | الأرشفة ومن نفذها |
| created_at / updated_at | التواريخ |

نطاق center واحد للشبكة. الوكلاء اختياريون. legacy_private نوع انتقالي لحفظ عزل الملكيات الحالية، وليس خيارًا في واجهة إنشاء النطاقات.

يضاف managers.scope_id وparent_agent_manager_id: موظف المركز يتبع نطاق المركز، والوكيل يتبع نطاقه، وموظف الوكيل يتبع النطاق نفسه ويرتبط بوكيله. المدير الرئيسي لا يحتاج نطاقًا مقيدًا. لا يُنشأ وكيل تابع لوكيل. تستخدم بيانات الاسم والهاتف والملاحظات الحالية؛ يضاف contact_email الاختياري عند الحاجة، وجدول manager_contact_numbers للأرقام الإضافية بدل إنشاء جدول وكلاء مستقل.

تحقق الخادم داخل المعاملة من أن الوالد وكيل فعّال، وأن الموظف في نطاقه، وأن مالك نطاق agent حساب وكيل. هذه قيود على صفوف متعددة لا يكفي CHECK وحده لفرضها. تُستخدم مفاتيح أجنبية مركبة حيث يمكن ضمان تطابق النطاق؛ يجب حل ترتيب إنشاء الجداول والعلاقات الدائرية في SQL.

## مجموعات الصلاحيات

تضاف permission_groups.scope_id، ويستبدل تفرد الاسم العام بتفرده داخل النطاق. ترتبط مجموعة المستخدم الفرعي بنطاقه ذاته. قاموس permissions يبقى عامًا داخل قاعدة الشبكة، والمنح مستقلة في permission_group_permissions.

صلاحيات موظف الوكيل الفعلية = صلاحيات مجموعته المتاحة ∩ صلاحيات مجموعة الوكيل المتاحة. غياب المنح، تعطيل المجموعة أو الحساب أو النطاق يمنع الوصول. تعطيل الوكيل يمنع موظفيه أيضًا. جميع هذه الشروط تُقرأ على الخادم، وليست مجرد إخفاء أزرار.

تضاف صلاحية مستقلة agents.staff.manage غير principal_only للسماح للوكيل بإدارة موظفيه فقط. تبقى managers.manage وpermission_groups.manage الحالية للمدير الرئيسي. إن مُنح الوكيل إدارة مجموعات موظفيه، تستخدم صلاحية مستقلة agents.staff_groups.manage وتبقى المنح محصورة ضمن صلاحياته. الوكيل لا يغير مجموعته الخاصة ولا ينشئ وكلاء ولا ينقل ملكيات بين النطاقات.

## ملكية المشتركين والتصنيفات

يضاف scope_id إلى customers وcustomer_categories. created_by_manager_id يبقى لتوثيق المنشئ، ولا يحدد الوصول. manager_id الحالي يُحفظ أثناء الانتقال كمرجع ملكية سابق إلى أن تتوقف جميع الاستعلامات عن استخدامه لتحديد الوصول.

يضاف scope_id إلى customer_category_memberships، وتصبح المفاتيح الأجنبية (customer_id,scope_id) و(category_id,scope_id). لا يُربط مشترك بتصنيف من نطاق آخر. يستبدل تفرد اسم التصنيف داخل manager_id بتفرده داخل scope_id. العضويات المتعددة للمشترك تبقى مدعومة.

يرى المدير الرئيسي جميع النطاقات. الوكيل يرى نطاقه فقط. موظف الوكيل يرى نطاق الوكيل عند وجود صلاحية العملية. موظف المركز لا يرى نطاقات الوكلاء تلقائيًا. الوصول الاستثنائي من المركز، إن نُفذ، يحتاج جدول منح نطاقات صريحًا وصلاحية مستقلة؛ لا يُفتح ضمنيًا عند الترقية.

النقل بين النطاقات للمدير الرئيسي فقط. يجب نقل/فك روابط التصنيفات المتعارضة داخل المعاملة نفسها وتسجيل النطاق السابق والجديد في activity_log. تعطيل موظف لا يغير الملكية، وتعطيل الوكيل لا يوقف خدمات المشتركين.

## مناطق التخديم

جدول network_service_areas: id وname وaddress وlatitude وlongitude وscope_id الاختياري لربط المنطقة بنطاق وكيل، وstatus بقيم active/inactive/planned، وnotes وcreated_by_manager_id وarchived_at وarchived_by_manager_id وcreated_at وupdated_at.

الأسماء العربية للحالات: فعّالة، متوقفة، قيد التجهيز. الإحداثيات زوج اختياري بحدود صحيحة. مناطق التخديم منفصلة عن تصنيفات المشتركين ولا تمنح صلاحيات وصول بمجرد الربط. قاعدة التصميم الحالية: نطاق وكيل واحد اختياري لكل منطقة؛ تعدد الوكلاء للمنطقة يحتاج قرارًا مستقلًا لاحقًا.

## ترتيب الترقية والتوافق

1. قراءة نسخة المخطط الحالية وعلاقات الصفوف، ورفض التنفيذ على قاعدة المركز، والتحقق من النسخة الاحتياطية قبل DDL.
2. إضافة بيانات الشبكة الاختيارية دون تغيير القيم الحالية.
3. إنشاء النطاقات وإضافة أعمدة التوسع بطريقة انتقالية قبل فرض NOT NULL.
4. إنشاء نطاقات legacy_private تحفظ كل ملكية حالية منفصلة. لا تتحول الحسابات الحالية إلى وكلاء تلقائيًا ولا تُدمج بيانات موظفي المركز تلقائيًا.
5. نسخ مجموعات الصلاحيات المشتركة إلى كل نطاق مطلوب، مع حفظ المنح والأسماء، ثم ربط الحسابات بنسخ مجموعاتها داخل نطاقها.
6. تعبئة نطاقات العملاء والتصنيفات والعضويات، والتحقق من أعداد الصفوف وتوافق كل العضويات قبل استبدال المفاتيح الأجنبية القديمة.
7. نشر مسار المصادقة والإدارة والاستعلامات الذي يفرض النطاقات والتحقق من الوكيل، ثم إنهاء القيود الانتقالية وإبطال الجلسات القديمة. لا يُنشر SQL تغيير الملكية وحده مع باك إند قديم.
8. تحديث قالب البيئات الجديدة وحارس الجداول وتوثيق المخطط وإصداره. نقل بيانات legacy_private إلى نطاق المركز/الوكيل يتم لاحقًا بإجراء صريح ومسجل.

DDL في MySQL ليس معاملة قابلة للتراجع الكامل؛ سكربت الترقية يجب أن يكون ذا مراحل قابلة للاستئناف، مع فحوص قبل كل مرحلة وإيقاف واضح عند فشلها. لا تُحذف حقول أو جداول قديمة في أول ترقية. توافق مرحلة الانتقال مع إنشاء مستخدم جديد وتوليد بيئة جديدة يجب تحديده قبل اعتماد SQL.
